做智能硬件时，“模式”是很容易写得简单、做起来复杂的一类需求。

PRD 里可能已经写了：**正常、待机、休眠、专注、开会、离席**。但到了研发阶段，问题马上就会变成：待机后主控还开不开？休眠还能不能语音唤醒？开会时摄像头要不要工作？专注模式会不会主动说话？

这时会发现，**模式名称不是需求，模式下每项能力的状态才是需求。**

![](/blogs/robot_mode_state_table/834def2550edd07f.webp)

## 先别急着做表，先把模式分层

我一开始也把所有模式放在同一张表里。后来发现，**待机和开会根本不是一类东西**。

待机解决的是设备怎么省电；开会解决的是用户怎么少被打扰。混在一层，后面一定会出现状态互相覆盖的问题。

更合理的拆法是三层：

### 1. 设备运行状态

回答的是：**机器现在以什么硬件状态运行？**

常见包括：工作、待机、休眠、关机。

这一层主要定义主控、辅控、屏幕、网络、传感器是否工作，以及还能不能被唤醒。

待机和休眠看起来都像“机器人不动了”，但实际区别很大：待机通常保留快速唤醒能力，休眠则更偏向降低功耗和减少活动。

### 2. 场景模式

回答的是：**机器人现在允许做什么，不允许做什么？**

例如：可聊、专注、开会、离席。

专注模式的核心不是“换一个专注动画”，而是减少主动说话、主动动作、主动拍摄等打扰；开会模式通常会更严格，重点是避免突然发声、动作和采集。

### 3. 全局状态

还有一类状态会跨越前两层，比如：充电、低电、OTA、故障、高温保护。

所以一个机器人某一时刻完全可能同时是：

```text
运行状态：待机
场景模式：专注
全局状态：充电中
```

这比简单写“当前是专注模式”准确得多。

## 真正要交付的是一张能力矩阵

模式分层后，下一步就是把每个模式下的能力逐项定清楚。

至少要覆盖这些：

| 能力项 | 需要明确什么 |
|---|---|
| 主控 / 辅控 | 开启、关闭还是低功耗运行 |
| 麦克风 / 唤醒 | 是否监听、支持哪些唤醒方式 |
| 摄像头 | 是否工作、是否允许主动拍摄 |
| 电机 / 动作 | 是否允许动作、主动动作是否降频 |
| 在线 AI | 是否可用、是否暂停 |
| 网络 | 保持连接、低功耗连接还是断开 |
| 主动互动 | 会不会主动说话、提醒、做动作 |
| 退出 / 打断 | 怎么退出，谁能打断，打断后是否恢复 |

这样再说“开会模式”，团队看到的就不是一个名字，而是一组明确的能力边界。

## 最容易出问题的，是模式之间怎么切

单个模式定义清楚，只完成了一半。

例如用户进入专注模式后，10 分钟没有互动，设备要进入待机。这时有两个选择：

- 专注结束，切成待机；
- 专注继续保留，只是运行状态进入待机。

我更倾向第二种。

也就是：

```text
场景模式：专注
运行状态：待机
```

用户重新唤醒后，机器人仍然遵守专注规则，不会突然恢复主动聊天和主动动作。

这也是为什么**运行状态和场景模式必须拆开**。

## 还要补一层：事件优先级

智能硬件里常见这种冲突：

```text
10 分钟无交互 → 进入待机
```

同时又有：

```text
10 分钟无交互 → 主动识别环境 → 给用户反馈
```

两条单独看都合理，放在一起就会冲突：主控准备下电时，谁来做识别？

这类问题不能靠补一句文案解决，最终都要落到：

> **状态 + 事件 + 优先级 + 打断恢复。**

所以一张完整的模式表，至少要回答三个问题：

1. **开还是关？** 每项能力是开启、关闭、低功耗还是按条件开启。
2. **能不能被唤醒？** 语音、按键、触摸、红外、App，哪些入口还有效。
3. **会不会主动打扰？** 是否主动说话、拍摄、提醒或做动作。

## 定义稿里，要把“事实”和“建议”分开

这一步很重要。

产品经理最容易犯的错误之一，就是把自己的建议写成已经确认的需求。

我现在会把内容分成四类：

- **事实**：现有 PRD、方案或研发已经明确；
- **建议**：基于产品目标和成熟做法提出的定义；
- **待确认**：需要产品、客户、研发共同拍板；
- **待验证**：必须通过硬件、嵌入式和实机测试确认。

例如“待机后主控关闭”可能是事实；“开会模式建议关闭主动动作”只是建议；“休眠后是否保留语音唤醒”可能还在待确认；“低功耗下能保留多少传感器”则需要实机验证。

**智能硬件里，‘我觉得能做到’和‘已经验证能做到’，是两回事。**

## 行业里比较稳定的做法

不同产品不会完全一致，但公开产品里能看到几个比较稳定的方向：

- 待机和休眠通常会分层，不会完全等价；
- 会议、隐私类模式会明显降低主动打扰；
- 摄像头、麦克风、主动语音的边界会被单独定义；
- 场景模式本质上是一组能力组合，而不是换一张 UI。

这也是我认为模式定义最值得关注的地方：**不是给状态起名字，而是把边界说清楚。**

## 我现在会这样做模式定义

如果重新做一遍，我会按这个顺序：

1. 先把模式清单列清楚；
2. 区分运行状态、场景模式、全局状态；
3. 拆主控、感知、AI、网络、动作等能力；
4. 补进入、退出、唤醒、优先级和打断恢复；
5. 把事实、建议、待确认、待验证分开管理。

做到这里，一张“模式状态表”才真正具备工程价值。

它既能让研发知道该开什么、关什么，也能让测试知道什么结果算正确，还能让产品和客户对“待机”“休眠”“开会”这些词保持同一个理解。

## 写在最后

App 里的一个模式，很多时候只是页面状态和功能开关。

但到了机器人这类智能硬件，背后还连着主控、传感器、摄像头、电机、网络和云端 AI。用户看到的只是一个“专注模式”，研发面对的却是一整套能力组合。

所以我更愿意把模式定义理解成一句话：

> **名词统一只是第一步，能力边界一致，才是真正的需求冻结。**
