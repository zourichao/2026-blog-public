> 原型，是一个想法第一次拥有轮廓。  
> 半径，是这个想法经过验证、迭代与落地之后，能够继续抵达的距离。

产品行业从来不缺想法。

真正困难的是：面对一个模糊的问题，能不能判断它值不值得做；决定做以后，能不能把它变成设计和开发真正可以执行的方案；上线之后，又能不能经得住真实用户和复杂环境的验证。

这也是我把这个网站叫做「原型半径」的原因。

这里不会只记录最后做出来了什么。我更想记录一个产品判断是如何形成的，一个方案为什么这样设计，以及它从想法走向现实的过程中，发生过哪些验证、取舍与修正。

---

## 01｜产品经理做的，很多时候是在减少不确定性

一个需求写进 PRD 并不难，难的是继续往下追问：

- 用户为什么进入这个页面？
- 操作成功以后，怎么确认结果？
- 网络超时、设备离线、权限拒绝怎么办？
- 重复点击或中途退出以后，系统该处于什么状态？

这些问题看起来很细，却往往决定了一个功能最后到底是“能演示”，还是“真的能用”。

以智能硬件 App 为例，用户看到的可能只是「连接设备」或「开始打印」，但按钮后面可能同时涉及：

> **App 状态 → 网络状态 → 设备连接 → 固件状态 → 任务下发 → 执行结果 → UI 反馈**

如果需求只写“点击按钮，开始执行”，这个需求其实远远没有完成。

产品经理真正需要确定的是：什么情况下可以开始，什么情况下不能开始；执行过程中出现异常怎么办；以及用户最终如何知道事情真的完成了。

**产品经理的价值，不是不断增加功能，而是持续减少不确定性。**

让用户少猜一步，让设计少补一种状态，让开发少反复确认一次，也让产品上线以后少留下一个没人知道怎么处理的灰色区域。

## 02｜原型不是交付物，而是一种验证工具

很多时候，我们会把原型理解成“给 UI 和开发看的页面”。

但如果原型只负责描述界面，它就失去了更重要的作用：**在真正投入开发之前，用更低的成本发现问题。**

我更愿意把原型分成四层。

### 2.1｜问题原型：先确定我们到底在解决什么

用户提出的需求，不一定就是问题本身。

例如用户说“这里能不能再加一个按钮”，真正的问题可能不是缺一个按钮，而是当前功能不好找。

所以第一步不是马上画页面，而是先确认：**用户为什么会提出这个需求？**

### 2.2｜流程原型：先把主链路跑通

一个功能最基本的流程应该先回答：

> **从哪里进入 → 做什么 → 系统发生什么 → 结果在哪里确认**

主链路确定以后，再补失败、中断、重复操作、用户取消和重新进入等异常场景。

很多后期返工并不是因为 UI 不够漂亮，而是一开始就没有把流程走完整。

### 2.3｜交互原型：把系统状态翻译给用户

系统内部可能有十几个状态，用户不需要全部知道。

用户真正需要知道的是：**现在发生了什么，以及接下来能做什么。**

正在连接、等待设备、执行中、已完成、执行失败、可以重试——这些状态什么时候出现，按钮还能不能点，页面能不能退出，都属于完整的产品规则。

很多时候，用户感受到的“稳定”，并不是系统永远不出错，而是即使出了问题，产品依然能明确告诉他发生了什么。

### 2.4｜技术原型：知道设计背后的边界

产品经理不一定需要写代码，但如果完全不了解实现方式，很多方案只能停留在理想状态。

接口什么时候返回、设备状态是不是实时的、App 和固件谁保存最终状态、弱网情况下有没有本地数据、新版 App 如何兼容旧版固件——这些技术条件都会反过来影响产品设计。

理解技术，不是为了替开发做技术方案，而是为了知道：**什么现在可以设计，什么暂时不能设计，以及哪里必须提前准备兜底。**

## 03｜真正的产品体验，发生在页面之外

做产品很容易把注意力集中在页面本身：布局是否合理、按钮放在哪里、流程是不是少了一步。

但用户体验并不只发生在屏幕上。

一次操作真正完成，通常经历：

> **用户发起操作 → App 判断状态 → 服务端 / 设备执行 → 返回结果 → UI 更新 → 用户确认**

任何一个环节出现问题，最后都会以某种形式回到界面。

产品只设计正常流程，异常状态就会留给开发临时处理；设计给出了即时反馈，但真实设备需要几秒钟才能返回；技术知道某个状态存在延迟，但产品没有设计等待过程。

最后用户看到的往往只有一句：

> **点了，没反应。**

每一个环节单独看可能都没有明显错误，但组合起来，体验就是失败的。

所以我越来越关注的不是“这个页面好不好看”，而是：**从用户发起操作，到最终得到结果，这条链路是否真的闭环。**

产品经理理解技术，不是为了成为工程师，而是为了把复杂系统转化成用户能够理解、能够控制、能够信任的体验。

## 04｜AI 让产出越来越便宜，判断会越来越贵

AI 正在非常快地改变产品工作。

今天已经可以用 AI 整理竞品、拆解需求、生成 PRD、设计页面结构、制作原型，甚至直接生成可以运行的代码。

过去需要几个小时完成的工作，现在可能几十分钟就可以得到一个不错的初稿。

但这反而让另一种能力变得更加重要：**判断。**

AI 可以快速生成五套方案，但它不知道当前项目还有多少开发资源，也不知道真实用户在哪一步最容易放弃，更不会主动告诉你：这个需求也许根本不应该做。

所以未来产品经理面对的问题，可能会从：

> 我能不能做出一个方案？

逐渐变成：

> **这么多看起来都合理的方案里，到底哪一个值得继续投入？**

AI 可以扩大探索半径，但方向怎么选、什么值得做、什么时候应该停止，依然需要人承担判断和结果。

## 05｜原型半径想长期沉淀什么

我希望这里长期遵循四个原则：

- **真实**：记录真实项目里的问题、限制和选择，也记录被放弃、被缩小、被推翻的方案。
- **验证**：观点不是结论，能用原型验证的用原型，能用数据验证的用数据，最终回到真实用户和实际交付。
- **迭代**：很多产品不存在“一次做对”，上线不是结束，而是下一轮判断的开始。
- **沉淀**：把一次项目经历整理成方法、规则、检查项和判断标准，才真正变成下一次还能复用的能力。

---

## 写在开始

「原型半径」不会只记录漂亮的最终页面。

我更想记录那些通常不会出现在作品集里的东西：

- 为什么一个需求最后被缩小了；
- 为什么某个异常状态必须提前想清楚；
- 为什么一个设计看起来正确，放进真实链路以后却走不通；
- 为什么有些功能技术上可以实现，产品上却不值得做；
- AI、设计和技术的变化，正在怎样重新定义产品经理的工作。

这些问题未必都有标准答案。

但如果每完成一个项目，都能多弄明白一个问题，把一次踩坑变成下一次可以复用的方法，那么产品能力的边界就会一点点向外扩展。

这就是我理解的「原型半径」。

**从一个想法开始，用原型把它带到现实，再用真实世界不断修正它能够抵达的距离。**
